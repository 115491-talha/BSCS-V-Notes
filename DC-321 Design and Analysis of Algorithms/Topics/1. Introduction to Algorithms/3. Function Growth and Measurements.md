# 6. Growth of Functions

## 6.1 Meaning of Growth of a Function

The **growth of a function** describes how fast a function representing an algorithm’s **time or space complexity increases** as the input size `n` increases.

In DAA, we are not interested in:

* Exact values
* Small input sizes
* Constant factors

Instead, we analyze how the function behaves as:

```text
n → ∞
```

---

## 6.2 Why Growth Matters More Than Exact Time

Consider two algorithms:

* Algorithm A: `T(n) = 100n`
* Algorithm B: `T(n) = n²`

For small `n`, Algorithm B may appear faster.
For large `n`, Algorithm A will **always outperform** Algorithm B.

Thus, **growth rate dominates performance**, not constants.

---

## 6.3 Ignoring Constants and Lower-Order Terms

### Example

```text
T(n) = 5n² + 3n + 20
```

As `n` grows:

* `n²` dominates `n`
* Constants become irrelevant

So asymptotically:

```text
T(n) = Θ(n²)
```

This simplification is the foundation of **asymptotic analysis**.

---

## 6.4 Common Growth Rates (Intuition)

| Growth Rate  | Intuition                   |
| ------------ | --------------------------- |
| `O(1)`       | Independent of input        |
| `O(log n)`   | Input reduces exponentially |
| `O(n)`       | Proportional growth         |
| `O(n log n)` | Divide-and-conquer behavior |
| `O(n²)`      | Nested iteration            |
| `O(2ⁿ)`      | Combinatorial explosion     |

---

## 6.5 Growth Comparison Example

Assume input size doubles from `n` to `2n`:

| Function   | Effect             |
| ---------- | ------------------ |
| `O(1)`     | No change          |
| `O(log n)` | Small increase     |
| `O(n)`     | Doubles            |
| `O(n²)`    | Quadruples         |
| `O(2ⁿ)`    | Becomes infeasible |

This is why **quadratic and exponential algorithms do not scale**.

---

## 6.6 Graphical Interpretation (Conceptual)

If plotted on a graph:

* X-axis → Input size `n`
* Y-axis → Time or space

Then:

* `O(1)` is nearly flat
* `O(log n)` grows slowly
* `O(n)` is a straight line
* `O(n²)` curves sharply upward
* `O(2ⁿ)` grows almost vertically

# 7. Performance Measurements

## 7.1 Definition

**Performance measurement** refers to evaluating how efficiently an algorithm or program performs in terms of:

* Execution time
* Memory usage

There are **two distinct approaches**:

1. Analytical (Theoretical)
2. Experimental (Empirical)

---

## 7.2 Analytical Performance Measurement

### Definition

Analytical performance measurement evaluates an algorithm **mathematically**, without executing it.

It uses:

* Time complexity
* Space complexity
* Asymptotic notations

---

### Characteristics

* Platform-independent
* Input-size focused
* Predictive
* Used during algorithm design

---

### Example

Before implementing Merge Sort, we know:

```text
Time Complexity = O(n log n)
```

This allows comparison with:

```text
Bubble Sort = O(n²)
```

---

## 7.3 Experimental Performance Measurement

### Definition

Experimental performance measurement evaluates an algorithm by **executing it** and measuring:

* Actual running time
* Actual memory consumption

---

### Characteristics

* Platform-dependent
* Language-dependent
* Influenced by hardware and compiler
* Useful for optimization and tuning

---

### Example

Running the same sorting algorithm:

* In C++ vs Python
* On SSD vs HDD
* On different CPUs

Results may vary, even for the same algorithm.

---

## 7.4 Analytical vs Experimental Comparison

| Aspect                   | Analytical | Experimental |
| ------------------------ | ---------- | ------------ |
| Execution required       | No         | Yes          |
| Platform dependence      | No         | Yes          |
| Uses asymptotic analysis | Yes        | No           |
| Accuracy for large input | High       | Limited      |
| Used in DAA              | Primary    | Secondary    |

---

## 7.5 Why DAA Prefers Analytical Measurement

* Hardware changes rapidly
* Algorithms remain stable
* Scalability matters more than speed on small inputs
* Enables fair comparison of solutions

# 8. Asymptotic Complexity Table (Best → Worst)

Below is the **complete ordered table** of **time and space complexity growth rates**, from **most efficient to least efficient**.

### Ascending Order (Best → Worst)

| Order | Asymptotic Notation | Name         | Typical Examples                 |
| ----- | ------------------- | ------------ | -------------------------------- |
| 1     | `O(1)`              | Constant     | Array access                     |
| 2     | `O(log n)`          | Logarithmic  | Binary search                    |
| 3     | `O(√n)`             | Sub-linear   | Trial division                   |
| 4     | `O(n)`              | Linear       | Linear search                    |
| 5     | `O(n log n)`        | Linearithmic | Merge sort                       |
| 6     | `O(n²)`             | Quadratic    | Bubble sort                      |
| 7     | `O(n³)`             | Cubic        | Matrix multiplication (naive)    |
| 8     | `O(nᵏ)`             | Polynomial   | Nested loops                     |
| 9     | `O(2ⁿ)`             | Exponential  | Subset generation                |
| 10    | `O(n!)`             | Factorial    | Traveling salesman (brute force) |

---

### Key Observations (Exam Gold)

* `O(n log n)` is often the **best achievable** for comparison-based sorting
* Polynomial-time algorithms are generally **tractable**
* Exponential and factorial algorithms are **intractable**
* Small improvements in growth rate yield massive real-world gains

---

## Final Takeaway

* **Growth of functions** explains *why* algorithms scale or fail
* **Performance measurement** can be theoretical or experimental
* **Asymptotic order dominates all constants**
* Choosing the right algorithm matters more than choosing the fastest hardware
